# 接手提示词（短版）

> 用法：把**完整的对话记录**和下面这段一起贴给新平台。

---

这是 Draftless 的开发对话记录。你要接手继续做，不是重做。

项目在 `D:\typeless\fast-speak`，仓库 `lijiatu-1/draftless`，已发布。开工前先读 `docs/HANDOVER.md`（项目全貌、10 个坑、未完成清单），再跑一遍：

```powershell
npm run lint
npm run check
node_modules\electron\dist\electron.exe scripts\dev\eval-twostage.mjs
```

**四条铁律**（对话里的细节都围绕它们，违反就是白干）：

1. **用真实录音验证，不许凭感觉。** 录音在 `%USERPROFILE%\.draftless\data\Recordings\`。禁止用合成语音（SAPI）评测——它干净、没有口吃，按它估的参数会系统性偏小。这条已踩过。
2. **先穷举候选再调参。** 模型之间的差距是 20–50 倍，比任何参数都大。曾经调 `thinking_budget` 调到"每条都能变好"，其实是在拟合数据。
3. **不擅自改。** 不加功能（上下文其他七份、HTTP 兜底、修改跟踪、个人词典、"问任何事"、翻译、云同步——明确不做），不动仓库可见性，有两以上条路线就让他选。他说过"你为什么擅自就改了？我没有同意批准"。
4. **报告诚实。** 做到了什么、没做到什么、哪些是猜的，分开说。

**他判断效果不好的时候，先分清是哪一层**：听写 / 整理 / 投递 / 交互——四层修法完全不同，别一上来就改提示词。

**他的工作方式**：会直接指出问题（"你太想当然了""你一直在走歪路"），几乎每次都对，先接受再查证、别辩解。给具体案例（一条录音、一段输出）就去复现，别抽象成"效果不好"再猜。他有洁癖，不喜欢堆机制、留旧代码。他给的截图和数字是权威数据，别用你搜到的覆盖它。

**第一步**：读完文档、确认测试是绿的、跑一次评测亲眼看效果，然后**问他想解决哪一件**。不要自己挑。
